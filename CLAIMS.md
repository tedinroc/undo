# Claims

Each row says what is claimed, the command that checks it, where that ran, its label, the last date it ran (UTC) and the real hash it rests on, with its chain named. A row or a part of a row that has not run says **not yet run**. Every PASS, SKIP or FAIL line of `./verify.sh` carries one of these claim numbers, except the lines that say a tool is missing, a whole suite failed, or the config cannot be read; its INFO lines are totals, or a record read from `proofs/` that the run did not check again.

Re-run: `./verify.sh` (tier A then B), `./verify.sh A`, `./verify.sh B`, `./demo.sh`. Sandbox rows: `scripts/build.sh`, then `UNDO_TEST_FILTER=<test> scripts/protocol-check.sh --test <file>` with `NEAR_SANDBOX_BIN_PATH` set; the whole suite is `scripts/protocol-check.sh`.

Labels: `[live-testnet]` NEAR testnet. `[live-mutinynet]` Mutinynet, a Bitcoin signet with test coins. `[replay]` a real hash fetched again and re-verified. `[consensus-lib]` libbitcoinconsensus, through rust-bitcoin. `[regtest]` a local bitcoind with standard relay policy. `[mock-signer]` a local NEAR node running the real wasm, with a mock signer in place of Chain Signatures. `[unit]` pure Rust, no chain. `[static]` a read of the source. No row is `[live-mainnet]`.

## Terms

`K_u`: the Bitcoin half of the spend key, in the vault's script. `K_s`: the NEAR-side key of the same seed, which signs proposals. `K_m`: the key Chain Signatures (NEAR's MPC network) derives for this vault; the contract asks it for the second signature. `K_e`: the cold key, offline, in the recovery file. `K_p`: the owner's passkey (P-256). G1, G2: the two live gates, G1 on NEAR testnet with the real signer, G2 with real Mutinynet coins. CSV: the Bitcoin timelock (OP_CHECKSEQUENCEVERIFY) after which the cold key alone can spend; BIP-68 is the relative-locktime rule it rests on. BIP-143: the segwit signature digest. `T_known`: the wait before a send to a destination the vault already knows, and before a new `K_s` from a rotation installs; 60 s on test coins. `T_new`: the wait before a send to a new destination while the guard is online, and before a loosening of the rules, a new known destination or a guard change lands; 5 min on test coins. `T_new_unguarded`: the wait before a send to a new destination while the guard is offline; 10 min on test coins. `T_recover`: the wait before a passkey recovery the cold key started can finish; 15 min on test coins. `T_stuck`: how long a coin must have been in a signing session before `reclaim` can send it back to the vault; 10 min on test coins. Guard: an account a vault names when it is made; the phone page names the relay. While the guard's heartbeat is fresh, a new destination waits `T_new`; when it stops, `T_new_unguarded`. Hold: the guard can put one hold on a pending request before its unlock, which moves the unlock later by `hold_ms`, 5 min on test coins; only with a model signature. Model signature: an ed25519 signature, by a key the operator registered for the guard model, over the contract's own request bytes and the model's answer. `new` registers none, and the `status` view says when none is registered.

## Who wrote the checks

Independent of this repository: libbitcoinconsensus (through rust-bitcoin's `bitcoinconsensus` feature), bitcoind on regtest, the Mutinynet node's answers, the NEAR testnet signer's own views and signatures. Every test, property and driver was written in this repository by the author with AI coding assistance (Claude). The sandbox's mock signer stands in for Chain Signatures and is labelled `[mock-signer]` wherever it is used.

## Not claimed

A catch rate; protection against coercion, or against a stolen passkey and spend key together; an audit; privacy; any first; any user count.
